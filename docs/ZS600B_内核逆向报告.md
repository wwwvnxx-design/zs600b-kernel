## 1. 逆向成果

### 1.1 DTS（完全攻克）

两条独立路径互相验证：

1. 设备活体 `/sys/firmware/devicetree/base`（root 可读，完整 dt 树）
2. `boot.img` → second 段 → RSCE 容器 → `rk-kernel.dtb`

```
boot.img (6848512 B, ANDROID! v0, page=16384)
├─ kernel    @ 0x004000  len 5137552   (zImage, 自解压头 0x016f2818)
├─ ramdisk   @ 0x4EC000  len 1337776   (gzip)
└─ second    @ 0x634000  len 335872    (RSCE 容器)
     ├─ header 512 B: magic "RSCE", ver 0x00010101, part_num 3
     ├─ index  @ 0x200: magic "ENTR" + name[252] + ... + size
     └─ dtb    @ 0x800  len 143803      (magic d00dfeed)
```

反编译产物：`output/root/re/dji_orig.dts`（6803 行 / 329 KB）

**USB 节点全貌**（这是整个问题的地图）：

| 节点 | compatible | 驱动 | 说明 |
|---|---|---|---|
| `usb@ff500000` | `rockchip,rk3288_rk_ehci_host` | rockchip_ehci_host | EHCI，bus1，端口被板载 WiFi 占用 |
| `usb@ff520000` | `rockchip,rk3288_rk_ohci_host` | ohci-rockchip | EHCI 伴生 OHCI |
| `usb@ff540000` | `rockchip,rk3288_usb20_host` | **dwc_otg** | **USB-A 口，bus3** |
| `usb@ff580000` | `rockchip,rk3288_usb20_otg` | **dwc_otg** | micro-USB OTG，bus2 |
| `usb@ff5c0000` | `rockchip,rk3288_rk_ehci1_host` | ehci1 | 无 status 属性，无引出端口 |

`usb@ff580000` 带 `rockchip,usb-mode = 0`（OTG 模式）。

### 1.2 boot header（完全解析）

- 标准 `ANDROID!` v0，**page_size = 16384**（不是 2048，此处曾是坑）
- 三段偏移见上图；`dt_size = 0`（DTB 走 second 段，不走 RK 扩展字段）
- **尾部 8192 B 全 0**：无 AVB、无 `TRUST`、无 RSA 签名块、无 `SEANDROIDENFORCE`
- 全文件扫 `AVB0` / `signature` / `TRUST` 均无命中

> 顺带纠正一个长期误判：**kernel 分区（mmcblk0p4, 16 MB）全 0**。zImage 只存在于 boot.img 内，改内核 = 只改 boot 分区（p5），不必碰 kernel/resource。

分区表与 `/proc/cmdline` 的 mtdparts 一一对应（单位 512 B）：

```
p1 uboot 4MB | p2 misc 4MB | p3 resource 16MB | p4 kernel 16MB | p5 boot 32MB
p6 recovery 32MB | p7 backup 52MB | p8 cache 256MB | p9 kpanic 4MB
p10 system 3GB | p11 metadata 16MB | p12 userdata 3GB | p13 radical_update 64MB | p14 user
```

### 1.3 U-Boot（定位成功 + 验签判定）

`uboot_dump.bin`（旧产物）是 4 MB 全零，无效。真实 U-Boot 在 **eMMC 偏移 0x46000（LBA 560）**，不在 uboot 分区里。

- 版本：Rockchip 定制 U-Boot（含 `do_fastboot` / `do_rockusb` / `rkimage_handleDownload` / `rk_load_image_from_storage`）
- 默认环境：`bootcmd=bootrk`、`bootdelay=0`、**`verify=n`**
- 存在 `Secure Boot state: %d` / `Secure Boot Mode: 0x%x` 打印代码
- 但 `androidboot.securemode=1` 只是传给内核的参数，**boot.img 里没有任何可验的签名块**

**判定**：刷自定义 kernel 不会被 U-Boot 拒绝。且历史上本机已刷过改版 ramdisk（cmdline 里 `androidboot.selinux=disabled` 就是证据）。

### 1.4 内核真实反汇编（关键）

`/proc/kallsyms` 默认被 `kptr_restrict=2` 清空地址。写入 0 后拿到真实符号：

| 符号 | 地址 |
|---|---|
| `dwc_otg_hc_start_transfer` | `0xc039e314` |
| `dwc_otg_hc_start_transfer_ddma` | `0xc039e030` |
| `dwc_otg_hcd_urb_enqueue` | `0xc03b24e4` |
| `dwc_otg_hcd_irq` | `0xc03b3eb4` |
| `DWC_WRITE_REG32` | `0xc03b98ac` |

用自编 `memdump`（`/dev/mem` mmap RAM 段，I/O 区被 `devmem_is_allowed` 拒绝）dump 物理 `0x39e000`，capstone 反汇编后确认：

```
c039e4fc  ldrb  r3, [r4, #5]
c039e500  bfi   r6, sb, #0x13, #0xa      ; HCTSIZ.pktcnt
c039e510  bfi   r6, r3, #0x1d, #2        ; HCTSIZ.pid
c039e518  bl    DWC_WRITE_REG32          ; write(r7+0x10 = HCTSIZ, r6)
c039e528  ldr   r1, [r4, #0xc]           ; hc->align_buff
c039e52c  add   r0, r7, #0x14            ; &hcdma
c039e534  ldreq r1, [r4, #8]             ; 否则 hc->xfer_buff
c039e538  bl    DWC_WRITE_REG32          ; write(HCDMA, dma_addr)
```

**结论：HCDMA 的写入逻辑是正确的**——`hc->xfer_buff` 在 Buffer DMA 模式下已是 `urb->dma + frame_desc->offset`（物理地址），不存在"虚拟地址当物理地址用"的经典错误。所以问题不在 DMA 地址计算。

顺带确认 HC 寄存器布局（此前我记错，漏了 HCSPLT）：

```
hcchar 0x00 | hcint 0x04 | hcintmsk 0x08 | hcsplt 0x0C
hctsiz 0x10 | hcdma 0x14  | hcdmab   0x18 |  每通道 0x20
```

## 2. 根因：ISO 带宽调度器计数崩溃

`/sys/kernel/debug/usb/devices` 里有铁证：

```
T:  Bus=03 ... Spd=480 MxCh=1
B:  Alloc=-37157048/800 us (724078%), #Int=0, #Iso=-676867
```

- `Alloc = -37157048 us / 800 us` → 带宽分配量溢出成负数，超容量 72 万倍
- `#Iso = -676867` → ISO 包计数为负

这两个字段是 `usb_hcd` 核心的 `bandwidth_isoc_reqs` / `bandwidth` 累加器。**负值只可能来自"释放次数远多于申请次数"**，即 `dwc_otg` 的 ISO 提交/回收路径收支不平衡。

配合此前 0xAA 哨兵实验（URB COMPLETED、包长正常、缓冲区零字节被写），整条因果链为：

1. ISO URB 提交 → `qh->interval` / `number_of_packets` 参与带宽计算
2. 调度器把通道排到错误的微帧，或 `hc->xfer_started` 状态没复位
3. 硬件发出 0 长度包（HCTSIZ.xfersize = 0）→ 硬件计数"完成"，但一个字节没搬
4. 驱动照常 `giveback`，每次多减一次带宽计数 → 累积成负

这也解释了为什么 `uvcvideo`（系统相机 App）和 `libusb`（自己写的 `uvc_cap`）**两条完全独立的代码路径都黑屏**——缺陷在内核驱动层，不在调用方。

**为什么 bulk 正常**：RTL-SDR 走 bulk 传输，不经过周期性调度器，所以计数器和通道状态都不受污染（bus3 之外的两条总线 `#Iso=0` 也印证了这点）。

**dwc2 路线为何不可行**：`rockchip-linux/kernel` 的 `release-3.10` 分支里 `drivers/usb/` 下只有 `dwc_otg_310`（正是 dmesg 打出的 `version 3.10a 21-DEC-2012`），**没有 dwc2 目录**。要编入 dwc2 得把主线 4.x 的整个驱动移植过来，工作量与风险都远超修 dwc_otg。

## 4. 唯一硬阻塞：编译环境

| 需求 | 现状 |
|---|---|
| `wsl.exe` | **被本机安全策略（程序黑名单）封禁**，无法批准绕过 |
| docker / podman | 未安装 |
| make | 未安装 |
| ARM 交叉 gcc | 无（NDK 的 clang 编不了 3.10 内核） |
| NDK clang | 有，可用于编用户态工具（已用来编 `regdump`/`memdump`） |

可选出路：
1. **GitHub Actions 云端编译**（推荐）：免费 Ubuntu runner，把内核树 + DTS + config 推上去，产物下载。需要一个可写仓库。
2. **允许 WSL**：需要你在安全中心把 `wsl.exe` 从黑名单移除。
3. **MSYS2 + arm-none-eabi-gcc 4.9**：Windows 下编 3.10 内核，坑多（路径、perl、symlink），历史成功率不高。

## 6. 关于 REA

本次目标为裸机 ARM 二进制（zImage 自解压体、U-Boot）与运行时内存，缺少 ELF 头与符号表，Ghidra 静态分析成本极高。改用 **kallsyms 真实地址 + `/dev/mem` 物理内存 dump + capstone 反汇编** 的组合，在同一次会话内拿到了 `dwc_otg_hc_start_transfer` 的逐条指令，证据强度等价且成本低一个数量级。REA 的取证分层（观察/推断/未知）框架沿用了。
